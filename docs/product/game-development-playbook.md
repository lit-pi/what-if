# What-If 轻量游戏开发 Playbook

本文档为 What-If 借鉴 Claude-Code-Game-Studios 中有用的部分，但不引入它完整的 Agent、hook 或规则系统。

目标是在保持仓库小而轻的同时，借用一种更有制作意识的游戏开发节奏。

## 来源启发

Claude-Code-Game-Studios 的组织方式像一个虚拟游戏工作室，包含专门角色、工作流阶段、系统设计模板和质量门禁。What-If 目前只需要其中轻量的部分：

- 用阶段门判断 MVP 什么时候可以推进。
- 在实现前，为游戏机制写系统设计文档。
- 用叙事、玩法、UI、技术风险和 QA 视角评审。
- 用验收标准保证功能可玩、可测试。

What-If 不应该复制完整工作室设置，因为本项目当前是零依赖静态原型，不是 Godot、Unity、Unreal 或生产规模游戏项目。

## 开发阶段

### 1. 产品框定

目的：明确玩家幻想和下游边界。

退出标准：

- 玩家角色可以在一分钟内被理解。
- 核心困境可以用一句话表达。
- 下游职责与 Silicon Factory 职责已经分开。
- MVP 剧本有清晰的起点、中段压力模式和结局承诺。

当前归属文档：

- `docs/context/silicon-factory-downstream-context.md`
- `docs/product/mvp-requirements.md`
- `docs/specs/what-if-scenario-catalog.md`

### 2. 剧本系统设计

目的：把故事转成状态、规则、触发器和可复玩的结果。

退出标准：

- 每个状态字段都有玩家可理解的含义和运行时 key。
- 每个主要 AI 角色都有压力函数。
- 每一幕都有预设行动、自由行动边界、焦点角色和转场规则。
- 结局优先级可以避免歧义或无结果。
- 至少六个结局可以通过文档化阈值到达。

当前归属文档：

- `docs/specs/undercover-demon-king.md`

### 3. 可玩运行时切片

目的：在不依赖不受约束 LLM 状态变化的情况下，让一次确定性流程可玩。

退出标准：

- 玩家可以开始游玩会话、玩完六幕并到达结局。
- 预设选项可以更新状态、旗标、焦点角色、反应和下一组选项。
- 自由行动可以被接受，并由确定性规则裁决。
- UI 在每回合后解释主要状态变化。
- 结算页解释为什么会触发该结局。

实现边界：

- 继续把 `index.html`、`src/app.js` 和 `src/styles.css` 作为原型表面。
- 本阶段不要引入 React、Vite、构建工具、账号、后端或市场概念。

当前实施文档：

- `docs/product/demo-implementation-plan.md`

### 4. 内容与资产切片

目的：用足够的视觉规划支撑第一个剧本，验证情绪、识别度和分享潜力。

退出标准：

- 第一个资产切片已经定义。
- 角色视觉锚点稳定。
- 事件图聚焦 1 个主角色和 1-2 个回应者。
- 结算卡背景留出清晰文字叠加区域。

当前归属文档：

- `docs/assets-prompts/undercover-demon-king-assets.md`

### 5. 上游反馈

目的：只有在玩法压力变清晰后，再把下游产品需求转成 Silicon Factory 需求。

退出标准：

- 原型识别出游玩中真正重要的人格字段。
- 角色记忆需求被描述为游玩会话级事件。
- 多 Agent 回合打包基于真实场景。
- GM 质量检查基于观察到的失败模式。
- 每个上游请求都有具体下游使用场景。

## 评审视角

在新增有意义的运行时行为或修改剧本规则前，使用这些视角检查。

### 叙事评审

检查：

- 场景是否保留了“卧底魔王”的幻想？
- AI 角色反应是否符合动机和既有记忆？
- 玩家自由度是否能改变路线，同时不破坏前提？
- 结局是否与之前选择有情绪和因果上的连接？

### 玩法评审

检查：

- 每个选择是否在身份、城堡、盟友或道德之间制造取舍？
- 状态变化是否足够可见，让玩家能学习系统？
- 多个结局是否可以到达，而不是依赖隐蔽技巧？
- 自由行动是否既有表达空间，又遵守约束？

### UI 评审

检查：

- 玩家能否在移动端理解当前场景、压力和可用行动？
- 默认只展示最重要的状态了吗？
- 结算页是否解释原因，而不只是显示标题？
- 警报是否绑定状态阈值，而不是装饰性噪音？

### 技术评审

检查：

- 状态 key 是否稳定，并裁剪到 `0-100`？
- 旗标和计数器是否显式记录，而不是从自由文本推断？
- 结局优先级是否确定性？
- 当前行为能否用 `pnpm check` 检查？
- 原型是否保持零依赖，除非有强产品理由？

### QA 评审

检查：

- 能否干净地开始新一轮游玩？
- 每一幕是否都能到达？
- 每个结局条件是否都能被有意测试？
- 没有具体分支命中时，是否有兜底结局？
- 自由行动处理是否避免不可能的瞬间胜利？

## 功能准入规则

实现新功能前，先写出或确认：

1. 玩家可见目的。
2. 受影响的状态字段。
3. 受影响的 AI 角色。
4. GM 裁决规则。
5. 结局或复玩影响。
6. 验收标准。

如果一个功能回答不了这六点，就先放在 notes，而不是进入实现。

## 暂不引入的内容

目前不要从外部工作室模板引入：

- 完整多 Agent 目录结构。
- Hook 自动化。
- Godot、Unity 或 Unreal 的引擎专用规则。
- 重型生产模板。
- 发布、商业化或平台认证流程。

这些以后可能有用，但在 MVP 证明玩法循环前，它们只会增加流程重量。
