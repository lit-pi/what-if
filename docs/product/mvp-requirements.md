# What-If MVP 需求

## 目标

围绕一个剧本构建可玩的移动端优先 What-If 原型：`假如我是勇者队伍里的卧底魔王`。

MVP 需要证明：一个下游系统可以把固定故事脚手架、状态驱动分支、AI 角色压力和 GM 裁决组合成一次短小、可复玩的互动体验。

## 用户体验

用户应该能够：

- 在一分钟内理解前提。
- 选择第一个剧本并开始游玩会话。
- 玩完六幕流程。
- 选择预设行动，或输入自由行动。
- 每回合后看到状态变化。
- 看到 AI 角色基于各自目标和关系状态做出反应。
- 到达一个确定性的结局，并理解原因。
- 回顾导致该结局的关键因果。

## MVP 范围

范围内：

- 一个剧本：卧底魔王。
- 移动端优先游玩界面。
- 每一幕都有预设选项。
- 自由行动输入框，初期用确定性规则模拟 / 裁决。
- 核心状态机。
- AI 角色反应槽位。
- 结局优先级系统。
- 带复玩反馈的结算页。
- 视觉提示词文档。

v0 范围外：

- 用户账号。
- 剧本编辑器。
- 实时多人。
- 完整 LLM 生产编排。
- 语音、视频或动画管线。
- 大型剧本市场。

## 运行时需求

每回合应产出：

- GM 叙述。
- 裁决结果。
- 状态变化和结算后状态。
- 旗标更新。
- 焦点 AI 角色。
- 角色反应。
- 可选插入事件。
- 下一组选项或结局候选。

服务端绝不能依赖不受约束的 LLM 自由文本来处理关键状态变化。服务端负责数值裁剪、结局优先级和允许的字段名。

## 验收标准

- 六幕流程可以从开局玩到结局。
- 没有任何结局分支会漏判到无结果状态。
- 至少六个结局可以通过文档化状态阈值到达。
- UI 展示当前场景、核心状态、焦点角色、预设行动和自由行动输入。
- 结算页可以解释为什么会得到这个结局。
- 文档明确 Silicon Factory 未来需要提供什么。
